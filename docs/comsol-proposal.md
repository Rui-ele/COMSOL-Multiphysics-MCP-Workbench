# AI 辅助 COMSOL 方案汇报材料

本文汇总项目目的、硬约束、可选技术方案及目标架构与任务编排，描述业务目标与建设方向，不代表各项能力已经实现。

## 1. 项目目的

建设一套面向 COMSOL 的自然语言助手，减少专家在信息传递和标准化操作上的时间消耗，使专家能够把主要精力用于问题定义、技术判断和结果审核，并提高 License 和工作主机的利用率。

当前研发流程存在三个主要效率瓶颈：

1. **模型上下文传递。** 借助 AI 辅助分析 COMSOL 问题时，专家需要先把模型结构、参数、设置和异常现象重新整理成自然语言提供给 AI。这个过程耗时，而且信息容易不完整，AI 给出建议后往往还需要专家继续补充上下文。

   通过 COMSOL MCP，AI 可以直接读取与当前问题相关的真实模型信息，辅助专家分析原因、提出排查思路和修改建议。专家仍负责定义问题、判断建议是否合理以及决定后续技术路线；AI 主要减少上下文整理和反复沟通的成本。

2. **技术判断落地为 COMSOL 操作。** 当专家已经确定修改方案后，仍需要人工在 COMSOL 中查找对应节点、修改设置并确认修改是否生效。对于明确、重复和标准化的操作，这部分会持续占用专家时间。

   通过 COMSOL MCP，AI 可以根据专家明确的任务完成节点定位、受控修改和修改后的回读核验。专家负责判断和决策，AI 负责把明确的技术意图转化为具体操作；专家再检查模型的实际变化。

3. **计算任务接续。** 单个计算任务启动后可以自行运行，但多个任务之间仍需要人工接续：前一个任务完成后，需要有人设置并启动下一个任务。

   下班后如果没有人在工作主机前，已经明确的后续任务就只能等待，导致夜间出现 License 和工作主机空闲。因此，系统应支持任务排队与接续执行，并允许专家通过员工助手的手机远程办公入口发起后续任务、查看进度和结果。手机断开连接后，工作主机上的计算仍继续运行。核心是减少任务之间因无人操作产生的空档，提高现有计算资源的有效使用时间。

目标协作流程：

> 专家定义问题和技术路线 → AI 获取真实模型上下文并辅助分析 → 专家确定方案 → AI 执行标准化操作并核验变化 → 专家审核模型 → 系统排队并接续执行已明确的计算任务 → 专家检查和验收结果。

## 2. 硬约束

1. **保密与数据安全边界**\
   模型、参数、结果及相关项目上下文必须按照公司的保密和数据安全要求使用。涉及外部 AI 时，专家需要根据公司规定和信息敏感程度判断哪些内容可以提供，不突破既有的数据边界。

2. **专家保持对关键操作的控制**\
   AI 可以辅助分析并执行明确任务，但不能在缺少约束的情况下自主修改模型或启动高成本操作。专家需要掌握关键决策和操作边界，并能够检查 AI 实际做了什么、必要时进行人工干预。网格生成、求解等操作应由专家明确触发或提前授权。

## 3. 可选技术方案

### 3.1 工作链路

从专家实际工作过程看，核心链路可以分为四个环节：

1. **获取模型上下文**\
   从当前 COMSOL 模型中读取与问题相关的结构、参数、设置和状态，使后续分析基于模型的真实状态，而不是主要依赖专家重新描述。

2. **专家与 AI 分析并明确任务**\
   专家提出问题并提供必要背景，AI 基于模型上下文辅助分析原因、讨论方案。专家负责判断并最终明确下一步需要执行的任务。\
   这一阶段既可以使用公司内部模型，也可以在符合保密要求的情况下，由专家选择必要信息与能力更强的外部 AI 讨论。

3. **执行与回读核验**\
   对专家已经确认的任务，系统完成具体 COMSOL 操作，并重新读取模型实际状态，确认修改是否真正生效，再交由专家检查。

4. **计算任务接续**\
   对已经明确的计算任务，在专家授权后启动计算，并支持任务状态保存、后续任务接续以及远程查看，减少非工作时间内 License 和工作主机的空闲。

因此，完整闭环可以概括为：

**获取上下文 → 专家 + AI 分析 → 专家明确任务 → 执行 → 回读核验 → 专家审核 → 必要时进入计算与任务接续**

### 3.2 技术概念

#### **员工助手**

员工助手是公司内部已有的**AI 交互入口和运行环境**，同时自带 **千问 3.6-27B-128K 的内部 API**。

因此，员工助手实际上可以拆成两部分看：

- **员工助手界面**：专家与 AI 交互的现成入口，同时提供手机远程办公入口；
- **员工助手 API**：提供公司内部可使用的大模型能力，也可以作为其他客户端或 Agentic 系统的模型来源。

目前员工助手现有界面的任务执行能力有限。如果希望它直接完成复杂的 COMSOL 多步操作，还需要进一步增加工具调用、Agent、Skills 等能力。

---

#### **大模型 API**

大模型 API 提供系统中的语言理解、推理和任务整理能力。

目前可以考虑的来源包括：

- **员工助手自带的千问 3.6-27B-128K API**：当前已经可以获得，接入成本较低；
- **公司其他内网模型 API**：要么响应非常慢（每分钟也就走十几个 token），要么申请困难；
- **自行部署模型**：采购设备后在公司允许环境内部署模型，并自行提供 API。通常自部署模型为千问 3.8-27B-256K。

不同来源主要区别在于**模型能力、响应速度、上下文长度、可控性和部署成本**。

---

#### **COMSOL Chatbot**

COMSOL Chatbot 是 COMSOL Desktop 内置的 AI 交互界面，是连接模型服务和 COMSOL 的一个现成客户端。

COMSOL 6.4 已支持 OpenAI、Azure OpenAI 以及 OpenAI API-compatible provider，因此理论上也可以连接满足接口要求的公司内部或自部署模型。它还可以将模型树节点、整个模型、模型历史、图片和文本等作为上下文提供给模型。

它目前比较明确的能力包括：

- 在 COMSOL Desktop 内直接与大模型交互；
- 将当前模型相关信息作为上下文提供给模型；
- 回答 COMSOL 建模问题；
- 生成和调试 COMSOL API for Java 代码；
- 将生成的代码发送到 Java Shell，再由用户运行。

因此，COMSOL Chatbot 已经同时解决了一部分**交互界面、模型上下文获取和 COMSOL API 代码生成**的问题。

---

#### **COMSOL MCP**

现有 COMSOL MCP 是另一种连接 AI 与 COMSOL 的操作接口。它能够把 COMSOL 的读取和操作能力暴露给上层 AI 系统，使 AI 可以通过工具调用完成：

**读取模型 → 定位对象 → 执行修改 → 回读实际状态**

因此它更适合作为员工助手、自建客户端或其他 Agentic 系统背后的 COMSOL 工具层。

---

#### **Agentic Harness**

Agentic Harness 是位于**大模型和实际工具之间的任务执行层**。

普通 Chatbot 通常是：

**用户提问 → 模型回答**

而 Agentic Harness 需要支持：

**理解任务 → 调用工具 → 读取工具返回 → 判断下一步 → 再次调用工具 → 处理异常 → 返回最终结果**

因此，如果希望 AI 根据专家的一条明确任务，自主完成多步 COMSOL 操作，就需要某种形式的 Agentic Harness。

它既可以集成进员工助手，也可以存在于单独的客户端中，并调用员工助手提供的模型 API。

---

### 3.3 完整技术路线

基于上述组件，目前可以形成四类主要技术路线。

#### **方案 A：分析与执行解耦**

**COMSOL MCP 获取上下文 → 专家选择必要信息 → 外部强模型辅助分析 / 整理任务 → 专家确认 → 员工助手执行 → MCP 回读核验**

这条路线不要求同一个 AI 同时承担“复杂分析”和“内部操作”。

专家首先通过 COMSOL MCP 获得与问题相关的模型上下文。对于符合保密要求的信息，可以交给能力更强的外部 Chat AI，用于分析问题、讨论方案，并将专家最终确定的技术意图进一步整理成清晰的执行任务。

执行阶段回到公司内部，由员工助手接收明确任务，通过 Agentic Harness 调用 COMSOL MCP 完成实际操作和回读核验。

**优点：**

- 专家分析阶段可以充分利用能力更强的外部模型；
- 员工助手主要负责执行，不要求内部模型承担完整的专家级分析；
- “分析能力”和“COMSOL 操作权限”相互解耦，后续可以分别升级；
- 初期需要建设的内部 AI 能力相对较少。

**主要问题：**

- 专家需要在外部 AI 与员工助手之间传递上下文和任务；
- 需要设计较稳定的上下文输出格式和任务提示词，降低人工搬运成本；
- 外部 AI 可获得的信息范围需要由专家按照保密要求控制。

这条路线的核心思路是：

**强模型帮助专家思考，内部系统负责可靠执行。**

---

#### **方案 B：全部在员工助手中完成**

**专家 → 员工助手 → COMSOL MCP 获取上下文 → 内部模型分析 → 专家确认 → Agentic Harness 执行 → 回读核验**

这一方案将分析、任务定义和执行都集中到员工助手中。

优点是专家只需要使用一个入口，并且可以直接利用员工助手现有的 PC / 手机入口；模型上下文也可以完全留在公司允许的环境中。

但相应地，员工助手内部需要同时承担：

**理解项目背景 + 分析 COMSOL 问题 + 形成任务 + 多步工具调用 + 异常处理 + 结果核验。**

由于当前使用的是千问 3.6-27B-128K，同时现有界面的 Agentic 能力有限，为获得比较稳定的实际效果，可能需要进一步建设：

**项目提示词 / RAG + Agentic Harness + Skills + COMSOL MCP 工具定义。**

因此，这条路线的主要问题不是链路不可行，而是**为了弥补内部模型和 Harness 的能力，需要自己建设和维护较多上层能力**。

---

#### **方案 C：利用 COMSOL Chatbot**

**专家 → COMSOL Chatbot → 内部或自部署模型 → COMSOL 模型上下文 / API 代码 → 专家确认并执行**

这一方案尽量利用 COMSOL 已经提供的原生能力。

COMSOL Chatbot 本身已经能够获取模型上下文，并辅助生成 COMSOL API 代码，因此可以减少自己开发交互界面、上下文读取和一部分 COMSOL 专用能力的工作。

其背后的模型可以考虑：

- 员工助手 API；
- 公司其他兼容 API；
- 后续自部署模型。

其中，公司其他内网 API 由于当前响应速度或申请条件问题，实际交互体验可能较差；如果后续自部署模型能够提供速度和能力都合适的兼容 API，这条路线的可行性会明显提高。

**优点：**

- 直接利用 COMSOL 已有的模型上下文能力；
- 原生集成度高；
- 可以减少一部分自建 UI 和上下文读取工作的开发量。

**主要问题：**

- 当前形态仍然更偏向 Chatbot + API 代码辅助，而不是完整的多步 Agent 执行系统；
- 专家主要仍需要在 COMSOL Desktop 前使用，不天然提供员工助手的手机远程入口；
- 操作后的自动回读核验、复杂任务执行以及计算任务接续仍可能需要额外开发；
- 与员工助手 API 或自部署 API 的实际兼容性仍需测试。

因此，这条路线尤其适合作为一个**低成本 PoC 方向**：如果 COMSOL Chatbot 已经可以覆盖足够多的上下文获取和操作辅助需求，就可以减少需要自行建设的部分。

**适用条件：**COMSOL 6.4 官方文档说明，Chatbot 窗口仅在 Windows 版 Desktop 可用；这一路线需要在 Windows 环境中实际验证。[COMSOL 6.4 Chatbot 文档](https://doc.comsol.com/6.4/doc/com.comsol.help.comsol/application_programming_guide.15.14.html)

---

#### **方案 D：完全自建**

**专家 → 自建 UI → 自建 Agentic Harness → 内部 / 自部署模型 → COMSOL MCP → COMSOL**

这一方案不依赖员工助手现有 Harness，也不依赖 COMSOL Chatbot 的能力边界，而是自行搭建完整客户端。

模型既可以先调用员工助手 API，也可以后续更换为自部署模型。

**优点：**

- UI、Agent、Skills、权限控制、上下文管理和 COMSOL 工具调用均可以按照实际需求设计；
- 各组件彼此解耦，长期可控性最高；
- 更容易同时覆盖 PC 使用、手机远程入口和复杂的任务执行逻辑。

**主要问题：**

- 需要自行开发和维护的部分最多；
- 员工助手和 COMSOL 已有的现成能力无法充分复用；
- 在需求尚未完全验证前直接建设完整系统，前期投入较大。

因此，它更适合作为现有平台能力无法满足需求后的扩展方向，而不是必须首先采用的方案。

---

### 3.4 各路线都需要单独解决的计算调度

上述四类路线主要解决的是：

**模型上下文 → AI 辅助 → 专家确认 → COMSOL 操作**

而“提高 License 和工作主机利用率”的目标，还需要单独解决**计算任务的排队与接续执行**。

无论专家通过员工助手、COMSOL Chatbot 还是自建客户端进入，只要希望在下班后连续执行多个已经明确的计算任务，后台都需要具备：

**任务保存 → 排队 → 启动计算 → 监控状态 → 计算完成 → 自动启动下一项已确认任务**

的调度能力。

目前，**员工助手已经提供手机远程办公入口，可以作为远程提交任务、查看任务状态和结果的交互入口**。

---

### 3.5 当前建议

现阶段优先采用**方案 A：分析与执行解耦**，并以员工助手现有的千问 3.6-27B-128K API 作为第一阶段的内部模型来源。

专家在符合保密要求的前提下获取必要的模型上下文，结合外部强模型分析复杂问题，最终明确技术方案和操作边界。公司内部的 Agentic Harness 接收已经明确的任务，通过 COMSOL MCP 执行受控操作并回读核验，再交由专家审核。

这一选择将当前内部建设重点放在真实模型上下文和明确任务的可靠执行上。计算任务的排队与接续是各路线共用的后台能力，按 3.4 节单独建设；具体交互入口和模型来源可随实际使用效果调整。

## 4. 目标架构与任务编排

### 4.1 目标架构

推荐架构的核心是把“分析”和“执行”解耦，同时在两者之间建立稳定的任务协议：

**专家 → GPT / 外部强模型 → 结构化任务 → 本地 Agentic Harness → COMSOL MCP → COMSOL**

执行完成后，再沿相反方向返回：

**COMSOL → COMSOL MCP → 结构化结果 → GPT → 专家**

其中：

- **专家**负责定义问题、技术判断和最终确认；
- **GPT / 外部强模型**负责辅助分析，并把专家意图整理成适合本地系统执行的任务；
- **本地 Agentic Harness**负责按照任务协议调用工具并完成多步执行；
- **COMSOL MCP**负责读取模型、执行修改和回读实际状态；
- **任务状态与调度能力**负责计算任务的状态保存、查询和已确认任务的排队接续；具体承载方式按 4.4 节选择。

因此，GPT 在系统中不仅是“聊天助手”，还承担一层**任务编译**作用：

**把专家的自然语言意图转换成本地系统更容易稳定理解和执行的任务；再把本地系统返回的结构化事实转换成专家容易判断的信息。**

---

### 4.2 双向任务协议

为了降低自然语言在系统内部传递时的歧义，专家与 GPT 之间可以继续使用自然语言，但 **GPT 与本地执行系统之间应尽量采用结构化协议**。

协议需要解决两个方向的问题。

#### **GPT → 本地执行系统**

GPT 将专家已经明确的意图整理成结构化任务。

这里不要求完全取消自然语言，而是采用：

**固定字段 + 必要的自然语言描述**

例如固定表达：

**任务目标、操作对象、执行边界、预期结果**

复杂的技术要求仍可以保留为自然语言内容。

这样可以避免本地 Agent 每次重新猜测一段自由文本到底想做什么。

#### **本地执行系统 → GPT**

执行结果也应按照稳定结构返回，而不是只返回运行日志或自由文本。

核心是让 GPT 能够快速区分：

**实际读取到的状态、执行过的操作、核验结果以及异常情况。**

因此，这套协议的作用不是单纯定义 API 字段，而是建立一个稳定的：

**专家意图 → 可执行任务 → 实际执行事实 → 专家判断**

的信息闭环。

具体字段不需要一次性全部确定，可以随着 PoC 逐步稳定。

---

### 4.3 Agentic Harness 的建设范围

本地 Agentic Harness 不需要从零开发。

Codex、Claude Code、OpenCode 等工具本身已经提供 Agent 循环、工具调用、上下文管理和基础任务执行机制。这部分属于工具自身的 Harness，通常只能选择和使用，不能大幅修改其内部调度逻辑。

真正需要建设的是**项目级执行环境**，主要包括：

**规则文件 + Skills + MCP 工具**

其中：

- `AGENTS.md` 等规则文件规定系统边界、执行原则和核验要求；
- Skills 固化已经成熟的高频任务流程；
- COMSOL MCP 提供 Agent 实际可以调用的 COMSOL 能力。

因此，建设重点不是重新设计一个 Agent 框架，而是：

**定义好任务协议，并让现成 Harness 按正确规则调用正确工具。**

---

### 4.4 任务状态与调度

计算任务需要与用户是否持续在线解耦。

对于已经启动的计算，即使用户关闭员工助手或手机断开连接，COMSOL 计算仍应继续运行；系统需要能够保存并查询任务状态，使用户重新连接后可以继续查看进度和结果。

如果存在多个已经由专家确认的计算任务，则进一步需要支持：

**任务排队 → 当前任务完成 → 启动下一项任务**

因此，这部分可以分成两个层次逐步建设：

**任务状态持久化与查询 → 多任务排队和自动接续**

员工助手主要作为任务提交、状态查询和结果查看的入口；具体如何保持任务运行、记录状态和实现接续，则根据现有员工助手、Agent 工具和 COMSOL 运行机制选择最简单的实现方式。

---

### 4.5 建设方式

系统不需要先把所有接口、Agent 和 Skills 全部设计完成，再开始测试。

更适合采用逐步扩展的方式：

**选择一个真实 PoC → 定义所需任务协议 → 配置规则 / Skill → 补齐 MCP 能力 → 实际运行 → 根据结果修正**

先跑通最小闭环：

**获取上下文 → 生成结构化任务 → 本地执行 → 结构化返回 → GPT / 专家核验**

随后再逐步增加新的任务类型和计算调度能力。

因此，接口字段、规则文件和 Skills 都是在真实任务中逐步沉淀出来，而不是在项目开始时一次性完整设计。
